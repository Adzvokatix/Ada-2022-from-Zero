Projects and gprbuild

Volume 1 built every program with one gnatmake command. From now on programs have several files in several folders, so you'll write down how to build them once, in a project file, and let a tool called gprbuild follow it.

Why a project file

Think back to Volume 1. Every build meant typing gnatmake -q -gnat2022 -gnata and a file name, and forgetting -gnat2022 gave you strange errors. The compiler's leftover .o and .ali files piled up next to your code. And everything had to live in one folder, because that's where gnatmake looked.

Real programs have dozens of files, sorted into folders. A project file answers the build questions once, in writing:

  • where the Ada files are
  • where the compiler's leftovers should go
  • where the finished program should go
  • which file holds the main procedure
  • which switches to use

It's a short text file ending in .gpr. gprbuild reads it and does the rest. Think of it as the instructions taped to the lid of a toolbox: anyone who opens the folder knows how to put the program together.

Child packages

When a package grows, Ada lets you hang another package underneath it, called a child package. Its name is the parent's name, a dot, and its own name. Here's Greetings.Formal, for more polite occasions:

Four rules come with children:

  • The file name swaps the dot for a hyphen. Greetings.Formal lives in greetings-formal.ads and greetings-formal.adb. That's GNAT's naming rule.
  • The parent comes along. with Greetings.Formal; makes Greetings available too, which is why greet.adb could still call Greetings.Say_Hello.
  • A child sees its parent. Inside Greetings.Formal, everything in the spec of Greetings is usable without a with or a Greetings. in front.
  • A child can see its parent's private part, from its own private part and its body. That matters once you have private types to build on.

Two procedures called Say_Hello don't clash, because they live in different packages: one is Greetings.Say_Hello and the other Greetings.Formal.Say_Hello.

Remember

  • A project file (.gpr) says where the code is, where the leftovers and the program go, and which switches to use
  • Build with gprbuild -q -P name.gpr; clear up with gprclean -P name.gpr
  • Warnings don't stop the build, but read every one
  • Child package Parent.Child lives in parent-child.ads and parent-child.adb

Common mistakes

  • Saving the .gpr file inside src instead of next to it
  • Leaving a folder out of Source_Dirs, so gprbuild can't find a file in it
  • A dot instead of a hyphen in a child package's file name
  • Typing ./greet while in a different folder from Exec_Dir

Matching a target output

Every exercise shows a target output, and it's exact: the same characters and the same spaces. Spaces are where most near-misses hide, because the code often doesn't show where they come from:

  • Fore => and Width => pad a number on the left with spaces, to the width you ask for.
  • Spaces at the end of a line are invisible on screen.

Files and the command line

So far your programs have learned everything from the keyboard and forgotten it when they ended. This lesson gives them two new ways in: words typed after the program's name, and files on disk. Files are also a way out, and they outlast the program.

This lesson's folder and project

From here on, every lesson starts the same way: a folder, and a small project file in it.

There's no Source_Dirs line, so gprbuild looks for Ada files in the project's own folder. There's no Main either: this lesson has several programs, and you'll name the one to build each time, like gprbuild -q args.adb. And there's no -P: when a folder holds exactly one .gpr file, gprbuild uses it without being told.

Arguments: the words after the program's name

You've been doing this all along: in gprbuild -q args.adb, the words -q and args.adb are command-line arguments, handed to gprbuild when it starts. Your own programs can read theirs with the package Ada.Command_Line:

NameWhat it gives you
Argument_CountHow many arguments there are: a Natural, 0 if none
Argument (I)Argument number I, counting from 1, as a String
Command_NameHow the program was started, here ./args

The shell splits what you type at the spaces, so red green is two arguments. Quotes keep words together, and the quotes themselves aren't passed on: the first argument in the last run was two words. Every argument is a String, even 3. To use it as a number, convert it with Integer'Value (Argument (2)), as in Volume 1's lesson 4.

Asking for an argument that isn't there, like Argument (1) when Argument_Count is 0, raises Constraint_Error. Check the count first.

When a program ends, it hands the shell a number called its exit status. 0 means it worked; anything else means something went wrong. Scripts and other programs check it. Here's a program that adds up the numbers it's given, and refuses politely when there aren't any:

  • Set Set_Exit_Status (Failure) and write to Standard_Error when something goes wrong

  • Using Create on a file you meant to add to: it starts empty again

  • Opening a handle that's already open: Status_Error

Discriminants and variant records

In Volume 1 every record had a fixed shape: the same fields, the same sizes, every time. This lesson's records shape themselves, using a value you give when you create them.

This lesson's folder and project

A record that sets its own size

A String field in a record needs a size, and in Volume 1 you had to pick one: Name : String (1 .. 20). Too long wastes space and needs padding; too short and some names don't fit. A discriminant lets each record choose:

Length sits in parentheses after the type's name, so it's a discriminant: a field you fill in when the record is created, which the rest of the record can depend on. Here it decides how long Text is. Short holds 3 characters and Long holds 12, and both are Name_Tags.

You read a discriminant like any field, Tag.Length. You fill it in like any field too, in the aggregate: (Length => Text'Length, Text => Text). The two parts must agree: Text must have exactly Length characters.

[1 .. Tag.Length + 2 => '-'] is an array aggregate with a range: positions 1 up to Tag.Length + 2, every one a '-'. It makes the border exactly fit the name.

A default makes a record changeable

Give the discriminant a default value, and a variable declared without one becomes unconstrained: whole-record assignments may change its discriminant. The catch: the compiler must set aside enough room for the biggest record it could ever hold. With Natural, that's more than two billion characters, and GNAT says so:

The fix is a small range for the discriminant, so the biggest possible record is small too:

Variant records: one type, several shapes

A discriminant can also choose which fields a record has. A circle needs a radius; a rectangle needs a width and a height. One type can hold either:

This is a variant record. The case Kind is inside the record says which fields exist for each value of Kind. A circle has Radius and nothing else; a rectangle has Width and Height. Area uses an ordinary case statement on the same discriminant to pick the formula.

A few rules:

  • The case must be the last thing in the record. Fields every shape has go before it.
  • Every value of the discriminant needs a when, as in a case statement. when others => null; is allowed, for "no extra fields".
  • Each field name may appear only once in the whole record, even in different variants. A rectangle and a triangle can't both have a field called Height.

The same discriminant check stops it. Ada never lets you read a field the record doesn't have, which in some languages quietly gives you whatever bytes happen to be there.

Variant records or tagged types?

Variant records are the right tool when you know every kind up front, and you're the one who'd add a new one. Later in this volume, tagged types handle "kinds of things" the other way round: anyone can add a new kind without touching the existing code. Each has its place, and you'll see both.

Remember

  • A discriminant is a field, set when the record is made, that the rest of the record can depend on
  • Without a default, a variable's discriminant is fixed for life; with one, a whole-record assignment can change it
  • Give a defaulted discriminant a small range, because the compiler makes room for the biggest record
  • A variant record's case picks the fields; reading a field the record doesn't have raises Constraint_Error

Common mistakes

  • Assigning to the discriminant alone, like Tag.Length := 5;
  • An aggregate whose String doesn't have exactly Length characters
  • A defaulted discriminant of type Natural or Integer: the compiler warns about Storage_Error
  • Using one field name in two variants

Vectors: lists that grow

An array has a fixed size, chosen when it's declared. Real data doesn't sit still: a to-do list grows, a queue shrinks. A vector is a list that grows and shrinks as you go, from Ada's standard library of containers.

This lesson's folder and project

A first vector

There's a lot packed into the top of that program:

  • Ada.Containers.Vectors is a generic package: a package with blanks in it. It knows how to keep a list of something, but not what. You met one in Volume 1's lesson 15, when the guessing game made a random number generator from Ada.Numerics.Discrete_Random.
  • package Score_Vectors is new … fills in the blanks. Index_Type => Positive numbers the elements from 1, and Element_Type => Natural says what they are. The result is an ordinary package called Score_Vectors, made for lists of Naturals. Making a package from a generic like this is called instantiating it, and Score_Vectors is an instance.
  • use Score_Vectors; lets you write Vector instead of Score_Vectors.Vector.
  • Scores : Vector; starts out empty, with room for as many elements as you'll ever add.

Scores.Append (72) adds 72 at the end. It's the same call as Append (Scores, 72), written with the vector first, as if Append belonged to it. Ada allows this dotted form for operations of a type declared in the same package, and containers are usually written this way.

Scores.Length counts the elements. It returns an Ada.Containers.Count_Type, a type of its own rather than Integer, which is why the program needs the long Ada.Containers.Count_Type'Image to print it.

Reading and changing elements

Vectors are indexed like arrays: Scores (2) is the second element, and you can assign to it.

Going past the end

Same as arrays: Ada checks every index, and a missing element raises Constraint_Error instead of returning junk.

Loops over a vector

Three ways to walk through a vector:

  • for S of Scores loop visits each element. S isn't a copy: it is the element, so S := S + 5; changed the vector itself.
  • for I in Scores.First_Index .. Scores.Last_Index loop gives you the positions, when you need them.
  • when S >= 90 is the filter from Volume 1's lesson 8. It works on vectors too.

One thing you can't do is change the vector's length while a loop is walking through it:

Adding an element can move the whole list to a bigger space in memory, out from under the loop. Rather than risk that, the vector raises Program_Error, the exception for "the program did something it mustn't". Tamper is the library's word for it. Collect the new elements in a second vector, and append them after the loop.

A vector of Strings

Try making a vector of names with Ada.Containers.Vectors, and the compiler says no: every element of a plain vector must be the same size, and Strings aren't. "Ada" takes 3 characters and "Grace Hopper" takes 12. String is an indefinite type, like lesson 2's records with no default discriminant: you can't declare one without saying how big. For those there's Ada.Containers.Indefinite_Vectors, which works the same way and stores each element at its own size:

  • Instantiate first: package Int_Vectors is new Ada.Containers.Vectors (Positive, Integer);
  • Append, Insert, Delete, V (I), Length, Contains, Find_Index
  • for E of V loop visits each element, and assigning to E changes the vector
  • Strings and other indefinite types need Indefinite_Vectors

Common mistakes

  • Printing V.Length as an Integer: it's a Count_Type
  • Writing V (I)'Image instead of Element_Type'Image (V (I))
  • Adding to or deleting from a vector inside a loop over that same vector: Program_Error
  • Using Ada.Containers.Vectors for Strings instead of Indefinite_Vectors

Reductions

Volume 1's lesson 8 added up an array with Scores'Reduce ("+", 0). That one line is the simplest case of a reduction: boiling many values down to one. This lesson opens it up: what happens inside, how to reduce with your own functions and into your own types, and what parallel would add.

This lesson's folder and project

What 'Reduce does, step by step

A reduction has three parts: the values, a reducer that combines two things into one, and a starting value. It keeps a running result called the accumulator. The accumulator begins as the starting value, then each value in turn is combined into it. This program uses a reducer that reports every step:

The reducer's first parameter is the accumulator so far; its second is the next value; it returns the new accumulator. "+" is a function with that shape too, which is why Scores'Reduce ("+", 0) works. So does any function you write with it.

Values made on the spot

The values don't have to be stored anywhere. A value sequence in square brackets makes them as the reduction goes:

[for I in 1 .. 10 => I ** 2] reads as "for each I from 1 to 10, the value I squared". It's never stored as an array: each value goes straight into the reducer.

Threes wants only the multiples of 3. The standard lets a value sequence take a when filter, like a loop: [for I in 1 .. 20 when I mod 3 = 0 => I]. GNAT 13.3 rejects that form on a range, with "prefix of Reduce must be an iterated component". Filters do work in ordinary loops, and on sequences over an array or container, for X of …, as later examples show. For a sum, an if expression that gives 0 for the values to skip does the same job, because adding 0 changes nothing.

Largest uses Integer'Max as its reducer. It takes two Integers and returns one, which is all a reducer has to do. Its starting value is Integer'First, the smallest Integer there is, so any real value beats it.

Reducing into a record

The accumulator doesn't have to be the same type as the values. To average some numbers you need two running results, a total and a count, so the accumulator can be a record holding both. The reducer can also be a procedure that updates the accumulator in place:

The starting value is a whole record, (Sum => 0.0, Count => 0). Note 0.0, not 0: Sum is a Float, and Ada won't turn a whole-number literal into one. (The reference manual's own version of this example has exactly that slip.)

A procedure reducer takes the accumulator as in out and changes it, instead of returning a new one. Both forms are allowed; a procedure saves copying a big record at every step.

Containers reduce too

Every container from lessons 3 and 4 can be reduced directly, the same as an array:

No value passed the filter in None, so the reducer never ran: a reduction over nothing gives back its starting value. Pick a starting value that makes sense on its own: 0 for a sum, 1 for a product, Integer'First for a maximum.

A reduction needs a place to go

The language requires that the compiler can tell, from where the reduction is used, exactly which type its result should be. Inside 'Image it can't. GNAT's message shows its guess: it took the result to be a universal integer, the type of a bare number like 0, and then found the Integers in Scores didn't match. Give the result a typed home: store it in a constant first, as every example above does, or write Integer'Image (Scores'Reduce ("+", 0)).

Big numbers

Integer stops at about two billion (Volume 1's lesson 2). Ada 2022 added Ada.Numerics.Big_Numbers.Big_Integers, whose Big_Integer has no upper limit. A reduction computes 30 factorial, 1 × 2 × … × 30, which is far too big for Integer:

That's 33 digits. Two details here exist only because GNAT 13.3 needs them: the language allows Reduce ("*", 1), but this compiler can't resolve "*" for Big_Integer inside a reduction, nor read the literal 1 as one. A named function and To_Big_Integer (1) sidestep both.

What parallel would add

The standard also defines parallel reductions: Scores'Parallel_Reduce ("+", 0), or [parallel for I in 1 .. N => …]'Reduce (…). The values are split into chunks, each chunk is reduced at the same time on a different processor core, and then the chunk results are combined.

That only gives the right answer if the reducer is associative: grouping mustn't matter, so (a + b) + c must equal a + (b + c). "+", "*", Integer'Max, "and" and "&" are. "-" isn't: (10 − 4) − 1 is 5, but 10 − (4 − 1) is 7. An ordinary 'Reduce always works through the values in order, so "-" is fine there. In parallel it's an error. And because each chunk starts from one of its own values, a parallel reduction's values and accumulator must be of the same type, so average.adb's record accumulator couldn't run in parallel as written.

GNAT 13.3 doesn't implement any of the parallel forms yet:

So this course teaches the ordinary 'Reduce, which every Ada 2022 compiler runs, and keeps parallel to this description. Your own compiler may be newer: build parallel_try.adb to find out.

Remember

  • A reduction starts the accumulator at the starting value, then folds each value in with the reducer
  • The reducer is any function (Accumulator, Value) return Accumulator, or a procedure with in out Accumulator
  • [for I in A .. B => Expression] makes values on the spot; when filters work on for X of … sequences
  • An empty reduction gives the starting value
  • Store the result in a typed constant before printing it

Common mistakes

  • A starting value of the wrong type: 0 for a Float accumulator, 0 for a record
  • 'Reduce (…)'Image: the compiler can't tell the result's type
  • A starting value that changes the answer: 0 for a product, 0 for the maximum of negative numbers
  • Expecting "-" or "/" to give the same answer in parallel

Writing generics

Lessons 3 to 5 used generics: Vectors, Ordered_Maps and Generic_Sorting are each written once and made into a real package for whatever type you name. This lesson writes generics of your own: procedures, functions and packages with blanks for types, and even for other functions, that get filled in at instantiation.

One procedure, any type

Swapping two variables works the same whatever they hold: keep a copy of one, overwrite it with the other, put the copy in the second. Written as a generic, it's written once:

A generic comes in two parts, like a subprogram with a separate specification:

  • The generic declaration: the word generic, then the formal parameters, the blanks, then an ordinary procedure specification. type Item is private; is a blank for a type.
  • The body, written as usual, using Item as if it were a real type.

Swap itself can't be called: it's a pattern, not a procedure. procedure Swap_Integers is new Swap (Integer); instantiates it, filling Item with Integer, and that is a real procedure you can call. The blanks can be filled by position or by name, as in Swap (Item => Character).

A whole package can be generic too. This one provides a stack: a pile where the last thing put on is the first taken off, like plates. A type, or a package with state?

There's another way to write Stacks: no Stack type at all, with the array and the counter declared in the package body, and Push (X) working on that one hidden stack. Then the package is the stack. That shape is called an abstract state machine, and it's right when there should be exactly one of something in the whole program: lesson 7's Accounts keeps its next account number that way. Its cost shows as soon as you want two: every extra stack means another instantiation, and no stack can be passed to a procedure, because there's no type to name in the parameter.

A package that offers a type, as above, is an abstract data type. It's the usual shape for anything you'll want more than one of, and it's how every container in lessons 3 and 4 is built. When unsure, write the type.

Why bother?

You could copy Largest and edit it for every type. Then a bug fixed in one copy stays in the others, and every copy needs testing. A generic is written once and checked once; the compiler then checks every instantiation against its blanks, before the program ever runs. That's how the whole container library can work for types its authors never saw.

Remember

  • generic, then the blanks, then a specification; then a body; then is new makes something real
  • A formal type's kind decides what the generic may do with it: private, (<>), range <>, digits <>
  • with function … is <>; is a blank for a function, filled automatically when there's one with the right name and shape
  • A generic can't be called; only its instances can

Common mistakes

  • Calling the generic instead of an instance
  • Using + or < on a private formal type without asking for them
  • Forgetting to fill a with function blank that has no is <> default
  • Writing type T is private; and then passing String: that needs type T (<>) is private;

Limited types: things you can't copy

Everything so far could be copied with :=. Some things shouldn't be: an open file, a bank account with its own number, a lock that only one part of the program may hold. A copy would be a second, competing version of something that should exist once. Ada lets you say so: a limited type is one that can't be copied.

You've already met one

Lesson 1's File_Type is limited. A handle copied while the file is open would be a second grip on the same file, and closing one would leave the other pointing at nothing. So Ada forbids it:

The left side of := can't be limited. That's checked when compiling, so the mistake never reaches a running program.

Making your own

Add the word limited to a record type, and the same rule applies to it. Here every account gets a number when it's opened, and two accounts must never share one:

Three things to notice:

  • limited private combines lesson 12 of Volume 1 with this lesson. Clients can't see inside an Account, and they can't copy one or compare two with = either. The package decides everything that can be done with one.
  • A function can still return one. Mine : Account := Open ("Ada"); doesn't copy anything: the function builds its result directly in Mine. Trying to copy one

Both are refused: no copying, and no = unless the package writes one. If clients need to compare accounts, the package can declare a function "=" that compares numbers, and decide for itself what "the same" means.

A record with a limited part is limited too, because copying the record would copy the part. A record holding a File_Type is a good example: it can't be copied, but it can be passed around and used.

Access types: pointers

Every variable so far was made when its declaration ran and lived until its block ended. Some data doesn't fit that pattern: a family tree, a chain of train cars, anything whose size and shape you only learn while the program runs. For those, Ada can make objects on demand and give you an access value, a pointer, that leads to each one. Other languages call them pointers or references; Ada calls them access values, and their types access types.

This lesson's folder and project

new, .all and null

That second output line is the whole point and the whole danger of pointers: Q.all := 100 changed what P sees too, because there's only one Integer. Two names for one object are called aliases.

Following null

GNAT warned at compile time, and Ada stopped the program at run time with an access check, instead of reading whatever memory address 0 holds. In some languages that's a crash with no explanation, or worse, no crash.

A chain of records

Pointers come into their own with records that point to more records. Each node holds a value and an access value leading to the next node, and the last node's is null. The whole chain is a linked list:

  • type Car; on its own is an incomplete type declaration: a promise that Car is coming. It lets Car_Access be declared first, so Car can contain one.
  • new Car'(Cargo => Cargo, Next => Front) makes a car whose Next leads to the old front car. Then Front moves to the new one. Adding at the front means the list comes out in reverse order of adding.
  • Here.Cargo is short for Here.all.Cargo: with records, Ada follows the pointer for you.
  • The walk is the classic linked-list loop: start at the front, do something, move to Next, stop at null.

Promising "never null"

Many subprograms only make sense with a real object. Saying so in the parameter's type puts the check where the mistake is, at the call:

Giving memory back

Every new takes memory from the heap, and in Ada nothing gives it back by itself. A program that keeps calling new and forgetting the results leaks memory, and a long-running one can run out. Returning memory is done with a generic procedure from the library, Ada.Unchecked_Deallocation:

That's why Ada makes you instantiate Unchecked_Deallocation by name, and why lesson 9 shows how to make freeing happen safely and automatically.

  • Forgetting that Q := P copies the pointer, not the object
  • Following a pointer without checking for null

Tagged types: building on a type

Lesson 2 put circles and rectangles in one variant record. Adding a triangle meant editing that record and every case on it. Tagged types turn this around: each kind of shape is its own type, built from a common parent. A new kind is a new type, added without touching the old ones. This is Ada's object-oriented programming, and you've already used it twice: lesson 9's controlled types are tagged types.

This lesson's folder and project

A family of shapes

The new words, in the order they appear:

  • type Shape is tagged record: a record that can be extended. Every object of it carries a hidden tag, a label saying exactly which type it is. Lesson 11 shows what the tag is for.
  • type Circle is new Shape with record … end record; is type extension, as in lesson 9: a Circle is a Shape with a Radius added. It has X, Y and Radius. Shape is its parent, and Circle and Rectangle are derived from it.
  • Primitive operations. Move, Area and Describe are declared in the same package specification as Shape, with a Shape parameter. That makes them Shape's primitive operations, and every type derived from Shape gets its own copy, said to be inherited. Circle never declares Move, yet Wheel.Move (2.0, 3.0) works.
  • overriding replaces an inherited operation with the type's own version. A circle's area isn't 0.0, so Circle overrides Area.

The aggregate for a Circle names all its fields, inherited ones included: (X => 0.0, Y => 0.0, Radius => 1.5).

Calling the parent's version

Circle's Describe doesn't repeat the code for the position. It ends with Describe (Shape (C)), which calls Shape's.

Shape (C) is a view conversion: the same object, seen as a Shape. Calling Describe on that view picks Shape's version, which prints the position. Each type adds what's new about it and hands the rest to its parent. The conversion goes this way only: every Circle is a Shape, but not every Shape is a Circle.

Dotted calls

Wheel.Move (2.0, 3.0) means Move (Wheel, 2.0, 3.0). Lesson 3 called vectors this way, and lesson 9 called S.Push. It works for any tagged type's primitive operations, which is why lesson 6's untagged Stack needed Push (Plates, 'A').

Remember

  • tagged makes a record type extendable; is new Parent with record … end record extends it
  • Operations declared with the type in its package specification are primitive, and derived types inherit them
  • overriding replaces an inherited operation; the compiler checks there is one to replace
  • Parent (Object) views an object as its parent type, to call the parent's version

Common mistakes

  • Leaving out tagged, then trying to extend the type
  • Declaring an operation somewhere other than the type's package specification, and expecting it to be inherited
  • Leaving out overriding, so a misspelled name quietly adds a new operation
  • Converting a parent to a child type: Circle (Some_Shape) only works if it really is a Circle

Two loose ends from lessons 10 and 11. Shape's Area returns 0.0, which is no real answer, and nothing stops anyone declaring a bare Shape that isn't any particular shape. Interfaces: sharing an ability

A pet and a road sign have nothing in common as shapes, but they both have names. An interface is an abstract type with no fields at all, only abstract operations, and any type can take on as many interfaces as it likes, alongside its one parent. Like every tagged type that brings new operations, it's declared in a package specification:

  • type Named is interface; declares the interface; function Name (N : Named) return String is abstract; is what it requires. Naming has no body, because nothing in it has one.
  • Why a package? A tagged type's new operations only dispatch if they're declared in a package specification, next to the type. Declare Named and Name inside Named_Demo instead, and GNAT warns "not dispatching (must be defined in a package spec)", then refuses the overriding lines. Overriding an operation that already exists, as Pet and Sign do here, is fine anywhere.
  • type Pet is new Named with record takes the interface alone.
  • type Sign is new Rectangle and Named with record has Rectangle as its parent and promises Named too. A Sign is a Rectangle, so it's in Shape'Class, and also in Named'Class, so Greet accepts it.

One parent, any number of interfaces: that's Ada's answer to the question of a type belonging to several families. It avoids the confusion of a type inheriting fields from two parents, since interfaces have no fields to inherit.

Choosing what 'Image prints

Every type gets an 'Image in Ada 2022. For a record, it lists the fields in Ada's own notation, which is fine for checking but not for showing users, and GNAT's version even starts with a line break. The Put_Image aspect replaces it with a procedure of your own:

'Image builds its text in a buffer, and Put_Image names the procedure that writes into it: Buffer.Put adds text.

Put_Money is declared twice: first on its own, straight after the type, then with its body. The order matters.   • abstract on a type forbids objects of it; is abstract on an operation forbids leaving it out
  • Every concrete type derived from an abstract one must override its abstract operations
  • type T is interface; is all abstract operations and no fields; new Parent and Interface with record takes on one parent and any number of interfaces
  • with Put_Image => Procedure_Name chooses what 'Image prints; declare the procedure right after the type, and its body later

Common mistakes

  • Giving an abstract operation a body, or forgetting the is abstract
  • Declaring an object of an abstract type
  • Expecting an interface to carry fields
  • Writing the Put_Image procedure's body straight after the type, without declaring it first
  • Declaring an interface, or a tagged type's new operations, inside a subprogram: they won't dispatch

Rendezvous: tasks meeting

Tasks that only run side by side are of little use; they need to pass things to each other. In Ada, one task offers an entry, like a procedure other tasks can call, and accepts calls to it with an accept statement. When a caller and an accept meet, the two tasks stop together while the accept's statements run, then go their separate ways. That meeting is called a rendezvous:

  • The entries are listed in the task's specification, between is and end, the same way a package lists its procedures.
  • Accumulator.Add (10) is an entry call. If the task isn't at an accept Add yet, the caller waits; if the task gets to its accept first, it waits for a caller. Either way, neither goes on alone.
  • Sum belongs to the task, and only the task's own code touches it. The main program can only ask, through the entries.

The terminate choice answers a question every service has: when does it stop? It's taken when the task is waiting in its select and nothing could ever call it again, because the main program has finished. Without it, Counter would wait forever, and so would the program.

What delay really means

delay 0.2 means at least 0.2 seconds: the task may wake a little later if the computer is busy. That's fine for pauses, but timing can't be used to put things in order between tasks.   • Using delays to put tasks' work in order
  • A server loop without terminate, so the program never finishes

Protected objects: sharing safely

Lesson 13's tasks kept their data to themselves and passed values through rendezvous. Often several tasks need the same data: one counter, one queue, one best-so-far. Letting them all at it directly goes wrong in a way that's hard to see and harder to reproduce. A protected object is Ada's answer: data wrapped in operations that only one task can run at a time.

This lesson's folder and project

The problem: a race

Four tasks each add 1 to a shared counter a million times. The answer should be four million:

Those are two real runs, on a computer with two processor cores. Yours will show other numbers, and on a single core it may even come out right, which is the worst part: a race can hide for a long time.

Count := Count + 1 is three steps for the computer: read Count, add 1, write it back. Two tasks can both read 500, both add 1, and both write 501: one click lost. That's a race condition, a result that depends on which task happens to get there first.

The declare block holds the array of four tasks. A block waits for the tasks declared in it, as a procedure does, so the Put_Line after it runs only once all four have finished.

The fix: a protected counter

Right every time. A protected object looks like a package with a private part: operations in front, data behind. The difference is the guarantee: while one task is inside Increment, every other task that calls it waits its turn. The three steps can't be interleaved any more.

Waiting for a condition: entries and barriers

Sometimes a task shouldn't just wait its turn, but wait until something is true: until a queue has something in it, or has room. A protected entry has a barrier, a condition after when. A task calling the entry waits until the barrier is true, and Ada rechecks it each time a procedure or entry changes the data.

Here's a bounded buffer: a queue of fixed size between a task that makes numbers and a task that uses them. Put waits while the buffer is full, and Get waits while it's empty:

  • Slot is a modular type, mod Size: it counts 0, 1, 2 and then wraps back to 0, so First + 1 goes round and round the array. That makes the array a ring buffer: the queue chases its own tail around it.
  • The output can't come out in a different order: only the main program prints, and a buffer hands things out in the order they went in.

Protected objects or rendezvous?

Both make tasks cooperate. A rendezvous is a meeting between two tasks, good for handing over work and getting an answer. A protected object is a place, good for data that many tasks share. Protected objects are also cheaper: no task has to sit in a loop serving calls. Most modern Ada code uses protected objects for shared data, and keeps tasks for work that really runs in parallel.

Remember

  • Shared data changed by several tasks without protection gives a race: wrong answers, different every run
  • A protected object's procedures and entries run one task at a time; its functions only read
  • An entry's barrier, when Condition, makes callers wait until the condition is true
  • A block, like a procedure, waits for the tasks declared in it

Common mistakes

  • Trusting a race-prone program because it gave the right answer once
  • Changing data in a protected function: functions are read-only
  • A barrier that can never become true, so callers wait forever
  • Calling a long-running operation, such as delay or file input, inside a protected operation: everyone else waits too

Project: a word counter

Time to build something with all of it. wordcount reads the text files named on its command line, counts every word, and reports the most common ones, or every count as CSV for a spreadsheet. Three worker tasks share the files between them, so big jobs go faster on a machine with several cores. Every part comes from an earlier lesson:

Step 1: the folder and the project

Three small files to count, in data:

Step 2: splitting a line into words

Lesson 4's word counter split lines with an Unbounded_String. This version marks where each word starts, and it's a generic: whoever instantiates it decides what to do with each word.

A generic procedure's file is named after the procedure, like any other.

Step 3: the shared tally

Each worker counts its own file into its own map, with nobody else involved, then merges the whole map into the shared tally in one protected call. That's far less waiting than taking turns for every single word.

Snapshot returns a copy of the whole map, so the report can take its time with it without holding anyone up.

Step 4: the queue of files

All the file names go into the queue before any worker starts, so Take never has to wait: it's a protected procedure, not an entry. Workers report problems to the queue too, and the problems are kept in a set, so they come out sorted whichever worker found them first.

Take hands back an Unbounded_String, because an out parameter of type String would need its length fixed by the caller before anyone knows the name.

Step 5: the reports

A report is anything that can write out a tally. The interface says so, and two types fill it in. Choose turns the name of a format into a report object, so the main program never needs to know which kinds exist.

  • More_Often is the order for the text report: higher counts first, and equal counts alphabetically, so ties always come out the same way. Lesson 6's "<" => … hands it to Generic_Sorting.
  • The text report walks the sorted lines by position and stops after R.Top of them, or sooner if there are fewer words. Each report object can carry its own settings, like Top; that's what the record part of Text_Report is for.
  • Line'(…) is qualified, as lesson 11's shapes were. Vectors have two Appends, one adding an element and one adding a whole vector, and an unqualified aggregate could be read as either.
  • Line and everything about sorting live in the package body: no client needs them.

Step 6: the main program

Read it top to bottom:

  • Each worker loops: take a file name, count it into its own Local map, merge. Count_Words is Each_Word instantiated with a procedure that adds to Local: a generic filled in with an action, right where it's needed. A missing file is reported to the queue, and the worker carries on to the next one: an exception left unhandled would have silently ended the worker (lesson 13).
  • The options: --csv first means CSV, and the files start after it. The if expression picks First without a separate variable.
  • The crew: three workers in a block, which waits for all of them, so by the next line the tally is complete.
  • The report: Choose returns some kind of Report, and Output.Write dispatches to the right Write. Nothing in the main program mentions Text_Report or CSV_Report.
  • The problems go to standard error, with exit status 1, after the report.

Step 7: run it

The first run shared three files among three workers, but the counts can't depend on who read what: adding up is the same in any order, the map keeps words sorted, and ties are broken alphabetically. Run it as often as you like; the output doesn't change. The third run counted what it could, reported the missing file, and still finished with exit status 1, so a script using it would know something went wrong.
